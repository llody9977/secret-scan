Application security / Repository controls

Make secret scanning governable, not merely early

Secret scanning reduces the chance that repository access becomes production access. Detection matters, but so do timing, enforcement, reliability, bypass governance, and incident response.

This guide commits one fictional corpus, runs Gitleaks and TruffleHog against it on GitHub Actions, records what GitHub Secret Protection did with the same push, and assigns each control to a practical role. A clean scan means only that the configured detector did not report a match.

Defensive scope

This article and its executable example are for educational and defensive use on a local repository or a system you are explicitly authorized to test. The fixtures contain no live credential, contact no provider, and pair the vulnerable case with its mitigation.

The decision in one minute

Do not run every scanner at every gate

01

Keep local scans as feedback

Pre-commit and pre-push hooks can stop mistakes early, but per-clone installation and bypass mean they are not organisation-wide enforcement.

02

Govern the host boundary

Enable native push protection for supported patterns and govern bypass. It is the shared control that can prevent covered values from entering GitHub before CI.

03

Require portable policy centrally

Use required Gitleaks CI for merge policy and internal formats. Add TruffleHog discovery only when distinct detectors, sources, or approved provider checks close a named gap.

Foundations

What counts as a secret?

A secret is a value whose confidentiality is part of a security decision: possession lets a person or machine authenticate, authorize an action, decrypt data, sign an artifact, or impersonate a trusted party. This practical definition matches the lifecycle emphasis in the OWASP Secrets Management Cheat Sheet.

Access credentials

Passwords, API keys, personal access tokens, OAuth and session tokens, webhook signing secrets, and connection strings containing credentials.

Cryptographic material

Private SSH, TLS, code-signing and package-signing keys, symmetric encryption keys, recovery codes, and key-encryption keys.

Machine identities

Cloud access keys, service-account credentials, CI/CD deployment credentials, database passwords, and automation tokens.

Sensitive is broader than secret

A public key, certificate public portion, hostname, or OAuth client identifier normally does not authorize access by itself. Personal data and proprietary source code may still require confidentiality controls, but secret scanning is not a complete data-loss-prevention system.

Business risk

A small coding mistake can become a large authorization failure

A secret collapses an identity check into a reusable string or key. If that value is overprivileged, long-lived, or shared across environments, the direct effects can include unauthorized cloud or database access, data exfiltration, malicious package publication, deployment tampering, resource abuse, and service interruption.

The business effects follow from that access: incident-response labour, emergency rotation and downtime, customer notification, contractual or regulatory exposure, fraud and cloud spend, supply-chain impact, and loss of trust.

Private repositories are not secret stores

Private repositories are copied to developer machines, CI runners, backups, mirrors, integrations, and third-party applications. Their access controls can also be bypassed by a compromised user or token. The following incidents describe the mechanism and impact; they do not show that scanning alone would have prevented each event.

Uber2014 / 2016

Repository credentials enabled a second-stage data access

The US Federal Trade Commission alleged that a publicly posted AWS key with broad privileges enabled the 2014 access to driver data. In 2016, attackers used stolen credentials to enter a private source repository, obtained another access key, and copied data associated with about 57 million records.

Decision: “Private” reduces exposure; it does not make source control an appropriate credential store. Scope and repository access security determine blast radius.

US DOJ agreementFTC complaint
GitHub / npm2022

Stolen OAuth tokens exposed a cloud credential in source

GitHub reported that stolen OAuth tokens were used to download private repositories. Its investigation linked unauthorized npm infrastructure access to an AWS API key obtained from downloaded private npm repositories.

Decision: Attackers mine repositories for credentials that enable a second-stage pivot. Repository access and infrastructure access should not share one failure boundary.

GitHub incident report
CircleCI2023

A CI trust point concentrated customer secrets

CircleCI reported exfiltration of customer environment variables, keys, and tokens and told customers to rotate OAuth tokens, project API tokens, SSH keys, and other credentials.

Decision: CI secret stores are production trust boundaries. Reduce stored long-lived credentials and design rotation before an incident.

When Git already contains it

Deleting the line is not revocation

A later commit does not delete the earlier Git object. The value may remain in clones, remote branches, pull-request references, forks, caches, build output, logs, or backups. History rewriting can reduce future exposure, but it cannot make a copied value unknown again.

  1. 1
    Revoke or rotate first.

    Invalidate the credential at its issuing system. GitHub’s cleanup guidance explicitly puts this before repository rewriting.

  2. 2
    Establish the exposure window.

    Identify the first commit, every branch and surface containing the value, who could read it, and when revocation completed. Preserve the incident records required for investigation.

  3. 3
    Check for use.

    Review provider, identity, cloud, database, CI, and application audit logs for activity within that window and within the credential’s actual permissions.

  4. 4
    Replace the storage pattern.

    Move the value to an approved secret manager or workload identity flow, update consumers, and confirm the old credential no longer works.

  5. 5
    Remove residue deliberately.

    Clean current content, decide whether to rewrite history, coordinate with clone owners, and search issues, pull requests, wikis, logs, artifacts, images, packages, and documentation.

  6. 6
    Add a regression guard.

    Use a provider-documented test token or a fictional repository-only format. Never recommit the real leaked value as a scanner fixture.

Control effectiveness

Judge a gate by capability, timing, enforcement, operation, and governance

An early control is not automatically a governable control. A local hook can prevent a commit when installed and not bypassed. Required CI is centrally governed, but the branch content has already reached the remote. Host push protection is the shared preventive boundary for the patterns it covers.

Detection capability

Does the configured rule set find the organisation's actual credential formats without unacceptable noise?

Timing and enforcement

Does it run before the business event that matters, and can policy require it and fail safely?

Operation and governance

Are reliability, bypass, exceptions, audit events, ownership, revocation, and remediation reviewable?

Selection criteria

Use ten evaluation questions, not ten mandatory product features

No single scanner needs to cover every source, provider check, governance workflow, and commercial boundary. A criterion becomes mandatory only when the assigned control or business risk needs it. The practical requirement is that the control system has no unowned mandatory gap.

01

Coverage fit

Always test the provider versions, generic values, pairs, keys, encodings, and internal formats assigned to the control.

02

Placement and timing

Choose the point before the business event to prevent: commit, first remote exposure, merge, deployment, or later discovery.

03

Enforcement and governance

Mandatory controls need central authority, restricted bypass, audit events, ownership, and a required status or host policy.

04

Failure semantics

Confirm finding and error exit codes, timeout behaviour, fail-open paths, and actual branch-rule integration.

05

Custom/internal formats

When required, version engine-specific patterns, decoding settings, safe positives, negatives, and host dry runs.

06

History and source reach

Assign Git refs, archives, images, logs, collaboration content, object stores, and organisations to controls that can scan them.

07

Signal and validity

Measure noise and misses. If provider checks matter, govern egress, permissions, rate limits, credential handling, and indeterminate outcomes.

08

Output and exception safety

Redact values and give each narrow allowlist or bypass an owner, reason, scope, and review or expiry date.

09

Performance and reliability

Test representative histories, binaries, submodules, concurrency, and service limits before making a control mandatory.

10

Operational and commercial fit

Review routing, response, metrics, supply chain, maintenance, licence, plan, cost, and data boundary at the program layer.

Mandatory here

The central merge control needs tested file/Git coverage, a versioned custom rule, deterministic failure behaviour, full-redaction output, and branch-protection enforcement. Wider-source discovery and provider validation are separate jobs, not reasons to reject a suitable merge gate.

Why TruffleHog is described as broad discovery

“Broad” refers to where it can search and whether it can check candidates with providers, not a claim that it detects every file shape better. It can enumerate sources beyond one checkout—such as repositories across a GitHub organisation, some collaboration content, object stores, container images, and CI systems. The remote matrix reinforces the distinction: TruffleHog found PostgreSQL and GitHub-token shapes that Gitleaks missed, and also missed shapes Gitleaks found.

Custom formats need their own miniature test suite

  • Gitleaks: version a TOML rule with keywords and regex; add entropy or narrow allowlists only when required.
  • TruffleHog: configure keywords and one or more named regexes; optional character requirements and webhook checks add structure, but the feature is documented as alpha.
  • GitHub: on an eligible repository, dry-run before publishing a custom pattern and enabling push protection. This repository's endpoint returned “feature not available.”

Keep safe positives for every supported version of an internal format and negatives for placeholders, public identifiers, examples, and near-matches. Re-run them after pattern, scanner, decoding, or host-setting changes.

Experiment limitations

  • Fifteen positives and three negatives are a regression matrix, not enough to estimate production false-positive or false-negative rates.
  • Inputs are non-issued shapes, provider checks are disabled, and no result says whether a credential is active.
  • GitHub accepted one commit containing all scenarios; no block was offered, so bypass governance was not exercised.
  • The alert export is a point-in-time observation. Non-issued shapes, asynchronous timing, disabled validity checks, and unavailable custom patterns limit the conclusion.
  • TruffleHog JSON can contain raw matches, so the harness keeps it temporary and persists only safe metadata; Gitleaks reports are fully redacted.
  • No large-history, archive, image, non-Git source, collaboration-surface, provider-latency, or operating-cost benchmark was performed.

The practical design combines controls with different authority: local feedback, host prevention for covered patterns, required portable CI for merge policy and internal formats, and centrally scheduled discovery. Restrict direct pushes and administrative bypass if CI is meant to govern every production change.

Portable policy

Use Gitleaks as the merge baseline

It supports versioned custom rules, history, full redaction, local feedback, and required CI. The remote corpus supports this assignment, not a universal ranking.

Shared prevention

Enable native push protection

It can stop supported configured patterns before CI. This corpus was accepted, so test current provider versions, custom-pattern eligibility, service limits, and bypass settings.

Named residual gap

Add TruffleHog deliberately

Use its different detectors, source connectors, or provider checks for a named need. Promote it to CI only after measuring incremental coverage, noise, latency, egress, report safety, and licence impact.

A governed stack, not “use all tools everywhere”

Close a material host gap with a custom portable rule, an eligible host pattern, a justified second CI scanner, or frequent discovery. Otherwise accept it explicitly with an owner and review date. Choose from the secret inventory, remote scenario results, and governance model—not the product count.

Secret lifecycle

Store fewer secrets, and manage the remainder

The safest stored secret is one that does not exist. Prefer workload identity, short-lived federation, or dynamic credentials to a static key. For example, GitHub Actions OpenID Connect can exchange workflow identity for a short-lived cloud token rather than duplicating a long-lived cloud credential in GitHub.

Create narrowlyProvision by identityUse least privilegeAudit accessRotate or expireRevoke decisively

When a static secret is necessary, use a central secret-management system that provides encryption in transit and at rest, least-privilege access by workload identity, read/write/admin audit logs, automated rotation and expiry, separation by application and environment, revocation, and a tested recovery or break-glass process.

Do not store live values in examples

Source files, unit-test fixtures, .env.example, documentation, screenshots, issue bodies, pull-request descriptions, chat, and logs are all poor secret stores. Store only the reference, identifier, or lookup path the runtime needs.

Operating model

What to put into practice

  • Inventory secret types, issuers, owners, scopes, storage locations, consumers, rotation methods, and revocation paths.
  • Remove long-lived credentials through workload identity or dynamic secrets where possible.
  • Use Gitleaks at pre-commit and pre-push for local feedback, then enforce the same rules centrally because hooks are manually installed and bypassable.
  • Run central CI on every push and pull request, on merge pushes, and daily; make Gitleaks full-history gate the required branch or ruleset status.
  • Enable GitHub push protection when eligible, configure internal formats where the plan supports them, and test the actual repository settings, current token versions, limits, and bypass policy.
  • Add TruffleHog when its different detectors, broader discovery, or provider checks close a named business-risk gap.
  • Keep scanner jobs least-privileged, pinned, checksum-checked, redacted, and isolated from unrelated secrets.
  • Maintain safe positive and negative fixtures for provider and custom rules.
  • Give exceptions an owner, narrow scope, rationale, and review date.
  • Treat confirmed exposure as an incident: revoke, investigate, replace storage, remove residue, and add a guard.
  • Measure time to revoke and rotate, not only the number of findings.

What to remember

Secret scanning is a layered control, not a guarantee of absence and not a secret store. Use local scans for feedback, govern prevention at the host boundary where possible, enforce portable policy in required CI, and design every real credential for least privilege, short lifetime, audit, rotation, and revocation.
